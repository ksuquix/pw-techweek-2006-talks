01 · Foundations (kept short)

TCP in one slide

A TCP connection is a handshake plus an agreement: a specific process, listening on a specific port, on a specific host, willing to talk to you.

SYN
→
SYN-ACK
→
ACK
→
connection established
A "connection" is really just this three-way handshake completing. Nothing about DNS or TLS is required for it — this is the layer both of those sit on top of.
A RST packet tells whoever receives it that the other side is done — tear down the connection, hang up. It's how a refusal or an abrupt close gets communicated at this layer.
Ask the room
Common question: DNS resolves the name fine, and ping to the host succeeds. How many of you do this check?
Ping uses ICMP, not TCP — a completely different protocol. A firewall, security group, or NACL can allow ICMP (so ping works) while blocking or dropping the specific TCP port the app needs, or nothing may even be listening on that port at all. "The host is reachable" and "the port is reachable" are two separate questions — and answering the second one means understanding the routing layer underneath both. That's next.

03 · Foundations (kept short)

Reference: the terms from that diagram

Glance-only — talking points if the room has questions, not something to read line by line.

TermWhat it means
Localtraffic that never leaves the subnet — no route table hop involved at all
Routinga route table deciding where traffic from a subnet goes next
Forwardinga device (like a NAT Gateway, or an NLB) passing traffic along untouched, often translating the address — layer 3/4 only

Source of confusion: "route" is also used at the application layer — mapping HTTP methods and URI paths to handlers, or an API gateway proxying a path to a backend. Same word, completely different layer than the "routing" on the diagram.
04 · Tools

curl, netcat, Test-NetConnection, openssl s_client

Four tools, same underlying question: can I open a connection to this host and port?

$ curl -v https://app.purplewave.com/health
Speaks the application protocol on top of TCP — cares about the response, not just the connection.
$ nc -zv app.purplewave.com 443
Linux/macOS. Raw TCP, nothing on top — the purest "can I even open a socket" test.
PS> Test-NetConnection -ComputerName app.purplewave.com -Port 443
PowerShell's version of the same raw-TCP test, plus ping and route info.
$ openssl s_client -connect app.purplewave.com:443
Once TCP connects but something's still wrong — performs the real TLS handshake by hand (covered in depth in the TLS talk).
Ask the room
"Connection refused" and "connection timed out" both mean "it didn't work" — but what's actually different about them at the network level?
Refused means a packet got there and something replied — usually a TCP RST — telling you plainly that nothing's listening on that port (or it's actively rejecting you). Timed out means your packets went out and nothing ever came back: no RST, no SYN-ACK, nothing. That's a silent drop — almost always a firewall, security group, or routing problem, not the destination host actively saying no.
05 · Errors

Reading curl's connection errors

This is the true meat of the talk. Before curl ever gets to HTTP or TLS, it has to open a TCP connection — and the specific wording it uses tells you exactly which layer failed, if you know how to read it.

ErrorWhat it means
Could not resolve hostnot a TCP problem at all — DNS never gave back an address to connect to (see the DNS talk)
Failed to connect / Couldn't connect to servercurl's generic wrapper message — by itself, mostly unuseful; the real cause is whatever's appended after it. When it isn't, reach for nc -zv against the same host/port to get the specific reason curl won't say
Connection reset (by peer)the connection was established, then torn down mid-stream by an RST — different from refused, which never connected at all. Common causes: the app literally crashed while answering, a next-gen firewall inspected the traffic mid-stream and didn't like what it saw, or one side simply lost its internet connection outright
Connection timed outnothing answered at all within the timeout — packets went nowhere. You'll see it as a hang, not an instant error: the command just sits there until it finally gives up
No route to hostthe local machine or a router along the way has no path to that address
Empty reply from serverTCP connected fine — the app on the other end closed the connection without sending anything
SSL certificate problemTCP is fine — this is past that layer entirely. If it works with -k, it's a cert/trust issue, not a connectivity one (see the TLS talk)
HTTP 500TCP connected fine, this is entirely app-layer — a middleman couldn't get to the real application: the app itself is down or broken, or a load balancer can't route to it
SSL routines::wrong version numberTCP connected, but what came back wasn't TLS at all — classic sign of hitting a plain HTTP port with an HTTPS request
400 "The plain HTTP request..."the mirror image — hitting an HTTPS port with plain HTTP, and the server's telling you so in plaintext instead of failing the handshake
06 · Tools

Reading netcat's connection errors

No HTTP, no TLS, no assumptions about what's on the other end — just "can I open this socket." Same underlying causes as curl's errors; nc just says them more plainly.

# port scan / connectivity check, verbose, zero-I/O
$ nc -zv app.purplewave.com 443
# listen on a port, for testing the other direction
$ nc -l 8080
OutputWhat it means
Name or service not knownnot a TCP problem at all — DNS never gave back an address to connect to (see the DNS talk)
Connection ... succeeded!the port is open and something's listening
... failed: Connection refusedthe port is closed, or nothing is listening — the app might not be running, or a forwarder/proxy in front of it isn't listening. The box is up, nobody's answering the door
... failed: Operation timed outnothing answered at all — the same silent drop as curl's timeout
... failed: No route to hostno path to that address, from here or a router along the way
... failed: Network is unreachablethe local routing table has no route to that network at all — never even left the machine
Ask the room
nc -zv host port just hangs for 30+ seconds before failing, instead of failing instantly. What does that tell you, versus an instant refusal?
A hang means the packet is being silently dropped somewhere — most commonly a security group or firewall rule set to deny with no response, rather than reject. An instant refusal means a packet actually reached a host that responded (even if just to say "nothing's listening here"). Speed of failure is itself a diagnostic signal: instant = reachable but closed; slow = probably blackholed in transit.
07 · Tools

Reading Test-NetConnection's connection messages

Same raw-TCP question as netcat, but built in to PowerShell, and it bundles ping and basic routing info into the same output — the move when you're desperate for info on a Windows box and can't install netcat.

PS> Test-NetConnection -ComputerName app.purplewave.com -Port 443
OutputWhat it means
No such host is knownnot a TCP problem at all — DNS never gave back an address to connect to (see the DNS talk)
TcpTestSucceeded : Truethe port is open and something's listening — DNS resolved and the connection went through
TcpTestSucceeded : False (RemoteAddress filled in)DNS worked fine — something in the path is blocking or refusing the port specifically. PowerShell won't tell you which, unlike curl or nc
PingSucceeded : FalseICMP failed or is blocked — doesn't mean the TCP port is unreachable, just a different protocol entirely
Add -InformationLevel Detailed for the hop-by-hop route it took getting there (if the network supports it).
08 · The Twist

Zscaler: it's essentially a proxy

Not "interferes with the network" in some vague sense — it intercepts and changes properties at three specific layers already covered in this series, and knowing which one is misbehaving is most of the debugging.

DNS
Points resolution to Zscaler's own IPs instead of the real answer — same mechanism as the DNS talk's hijacking slide.
TLS
Opens its own new connection to the real backend, then hands you back a connection signed with Zscaler's own internal cert — not the backend's.
Connection
Builds a proxied TCP connection to the backend on your behalf — you're talking to Zscaler, Zscaler is talking to the destination.
nc -zv host 443
→
Zscaler proxy
accepts the connection
→
real destination
(maybe unreachable)
Ask the room
nc -zv to port 443 succeeds instantly on a Zscaler-managed machine, but the actual application still times out. How can the raw connection test pass while the app fails?
The TCP connection succeeded — just to Zscaler's proxy, not the real backend. Zscaler transparently intercepts the connection and terminates it itself; whether the actual destination is reachable is then entirely up to Zscaler's own ability to reach it on your behalf. A raw connectivity test from a Zscaler-managed machine tells you Zscaler accepted the connection, not that the real destination is reachable — test from off that network path to know for sure.
09 · Security

Beyond "is it routable": specific security layers

A route existing doesn't mean traffic is allowed. Each of these can independently block a connection that's otherwise perfectly routable — and each one has to say yes.

Zscaler
Intercepts and inspects — can silently drop traffic it decides not to forward.
NACLs
Subnet-level firewall. Stateless — needs explicit rules for return traffic too, often on ephemeral ports.
Security Groups
Instance-level, stateful. Allow-only — no explicit deny rule, just the absence of an allow.
Host firewall
iptables/nftables/Windows Firewall on the box itself — a rule here overrides everything upstream that said yes.
Kubernetes NetworkPolicy
Pod-level allow rules inside the cluster — a route to the pod's IP existing says nothing about whether NetworkPolicy permits it.
App policy
The application itself checking an allowlist, an API key, or an auth token — the last gate, entirely above the network layer.
Ask the room
Six layers, any one of which could be the culprit. How can you figure out which thing it actually is?
Narrow it down by splitting the problem, not by guessing layers in order:
  • Local vs. remote — try sshing (or connecting) to something else from the same box, and try the original target from somewhere else. If it fails everywhere from here, it's local; if it only fails to this one destination, it's something in the path to that destination specifically.
  • From a different vantage point — if you can spin one up, try it from a pod (or a different pod) inside the cluster, not just from your workstation.
  • Different ports — same host, different port. If other ports work fine, you've ruled out most of the routing-level layers and narrowed it to something scoped to that one port.
  • Let the connection error itself guide you — refused vs. timed out vs. reset point at different layers, per the tables earlier in this talk. Read the error before assuming which layer to check first.
  • Claude is great at this — if you have the access, it's genuinely good at poking in various places and seeing where things stop matching up.
Wrap-up

The debugging ladder

Isolate which layer is actually failing before assuming the whole network is broken — each rung has its own tool.

1. Does the name resolve?
dig / nslookup — DNS in Depth territory.
2. Does the port accept a connection?
nc -zv / Test-NetConnection — plain TCP, no app layer at all.
3. Does the TLS handshake succeed?
openssl s_client — TLS in Depth territory.
4. Does the application actually respond?
curl with the real request — the first layer where app logic, not networking, can be the cause.
You can usually start anywhere on the ladder — but let the errors and messages you get point you toward the next place to look.
