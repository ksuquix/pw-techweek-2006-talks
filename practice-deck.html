01 · Method

How to work a case

Four questions, asked in order, before touching anything. Every case after this slide runs through the same four.

1. What are the exact words?
Copy the whole error, errno and all. ENOTFOUND and EAI_AGAIN both say "DNS," but they mean different things.
2. Who said it?
The client library, a proxy (nginx, APISIX, Cloudflare), a load balancer, or the app itself? A 502 is a proxy talking about something behind it.
3. Which rung of the ladder?
Name, port, handshake, or app. The wording almost always tells you, once you know the decoder (two slides on).
4. When, and how wide?
One service or thirty? One pod or every node? Starting at a deploy, or at a steady rate for weeks? Blast radius points at the shared dependency.
The rungs are the debugging ladder from Connectivity in Depth, on the next slide. Once you've placed the error on a rung, test that rung, from the same place the error came from: the same pod, the same box, the same network path.
🥚 Easter egg
Datadog keeps about 7 days of logs searchable, so every case here is from the week of October 5–12, 2026. Nothing was cherry-picked from years of history. This is what a normal week looks like.
02 · Reference

The debugging ladder

From Connectivity in Depth. Isolate which layer is actually failing before assuming the whole network is broken. Each rung has its own tool.

1. Does the name resolve?
dig / nslookup — DNS in Depth territory.
Look at DNS / connectivity to DNS
2. Is the connection accepted / refused / reset / timed out?
nc -zv / Test-NetConnection — plain TCP, no app layer at all.
Look at Networking / Security / App actually running
3. Does the TLS handshake succeed?
openssl s_client — TLS in Depth territory.
Look at TLS config / mismatch
4. Does the application actually respond?
curl with the real request — the first layer where app logic, not networking, can be the cause.
Look at app logic / proxy config
You can usually start anywhere on the ladder, but let the errors and messages you get point you toward the next place to look.

03 · Reference

The decoder: same failure, three dialects

Node, Go, and nginx describe identical failures in different words. Learn to see the failure through the dialect.

Rung · what happenedNodeGonginx (errno)
Name · authoritative "no such name"ENOTFOUNDno such hostcould not be resolved
Name · resolver didn't answerEAI_AGAINlookup … :53: i/o timeout… timed out
Port · RST back, nothing listeningECONNREFUSEDconnect: connection refused(111: Connection refused)
Port · silence, packets droppedETIMEDOUTdial tcp …: i/o timeout(110) while connecting
Port · no route at allENETUNREACHnetwork is unreachable(101: Network unreachable)
Port · connected, then torn downECONNRESET / EPIPEconnection reset by peer / broken pipe(104) / (32: Broken pipe)
TLS · handshake didn't finishERR_TLS_… / UNABLE_TO_…x509: … / tls: …SSL_do_handshake() failed
App · connected, answer too slow(your timeout)context deadline exceeded(110) while reading response header
Watch out for i/o timeout in Go. It shows up on two different rungs. lookup X on 172.20.0.10:53: i/o timeout is a DNS query over UDP that got no answer. dial tcp 10.0.0.5:4222: i/o timeout is a TCP connect that got no answer. Read what comes before it.
04 · Case 1 · DNS

Database issue

service: checkdatabase-eastAWS Lambda~8,640 / day, every dayrung 1 · name
ERROR Invoke Error {"errorType":"Error","errorMessage":"getaddrinfo ENOTFOUND pw-production-us-east-1d.xxxxxxxxxxxx.us-east-1.rds.amazonaws.com","code":"ENOTFOUND","syscall":"getaddrinfo" …}
at Connection.connect (mysql/lib/Connection.js) → testConnection
Clue 1 · exact words
ENOTFOUND, not EAI_AGAIN. The resolver answered, and the answer was "that name doesn't exist." This isn't a flaky resolver. It's a firm no.
Clue 2 · when and how wide
One error roughly every 10 seconds, at a perfectly flat rate, all week. No spike at a deploy, no other services affected. Something scheduled is asking for the same missing name over and over.
Clue 3 · test the rung
dig pw-production-us-east-1d.….rds.amazonaws.com → status: NXDOMAIN. RDS publishes an instance's DNS name while the instance exists and removes it when the instance is deleted.
Verdict
The database isn't there. A health-check Lambda is still testing a database that was deleted or renamed. A sibling Lambda does the same against a -1b instance. Together they make about 121k errors a week, all noise. ENOTFOUND on a cloud-generated hostname usually means "that resource is gone," not "DNS is broken." The fix is to delete the check, not to touch DNS.

05 · Case 2 · DNS?

"ENOTFOUND" for a name that was never a host

geo-worker · prod EC2rabbit consumer · prodintermittent, ~110 hits
Database connection failed: getaddrinfo ENOTFOUND app_srv_worker
[getRabbitConnection] GetConnectionWithEnv Failed: Error: getaddrinfo ENOTFOUND amqp
Ask the room
Look closely at the two names DNS was asked to resolve. What's wrong with them, and should anyone be looking at DNS?
Neither one is a hostname. app_srv_worker is a database username, and amqp is a URL scheme. The code built a connection string, a URL parser split it in the wrong place, and the wrong piece got handed to DNS. Common causes:
  • an unencoded @, #, or / in the password (# starts a URL fragment, so everything after it disappears)
  • an env var that's empty or unset, so amqp://${HOST} collapses
  • a full URL passed into a field that expects a bare host
DNS did its job correctly. The name in the error is the name the code actually used. Read it before you blame the resolver.
Walking the ladder for this case · illustrative output
# rung 1 · the name from the error
$ dig +noall +comments app_srv_worker | grep status
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 5120
# rung 1 · the name that should have been used
$ dig +short mysql.prod.internal
10.0.5.86
# rung 2 · port
$ nc -zv 10.0.5.86 3306
Connection to 10.0.5.86 3306 port [tcp/mysql] succeeded!
# ✓ the real host resolves and connects. The network is fine, so look at the config:
$ printenv DATABASE_URL
mysql://app_srv_worker:****#****@mysql.prod.internal:3306/geo
# an unencoded '#' in the password: everything after it parses as a URL fragment
$ printenv RABBIT_HOST
amqp://rabbit.prod.internal:5672
# a full URL in a field that expects a bare host, so the library looks up "amqp"

06 · Case 3 · DNS

Eight services, 36 minutes, one problem

cluster: qa-green2026-10-09 22:14–22:50 UTCargocd, backstage, settlement, shipping, terms, cloudflared, …
dial tcp: lookup github.com on 172.20.0.10:53: read udp 10.101.x.x:…->172.20.0.10:53: i/o timeout

Ask the room
Seven different-looking errors from eight teams' services, all in the same half hour. How many problems are there, and where would you look first?
One. Every line is a name lookup, and the Go lines name the server: 172.20.0.10:53, the cluster's kube-dns ClusterIP. External names (github.com), internal zones (cliquidator.info), and bare in-cluster Service names (item-service) all failed together. That means the problem is the resolver they share, not any one of the names. EAI_AGAIN means "temporary failure, try again," which is a very different message from Case 1's firm ENOTFOUND.

First moves: kubectl -n kube-system get pods -l k8s-app=kube-dns, then a lookup from a throwaway pod on the same node. A node-memory-pressure alert fired in the same window, so a starved CoreDNS pod is the leading theory. It's a theory, though, not a confirmed cause.

🥚 Easter egg
Why only a theory? CoreDNS's own logs aren't shipped to Datadog, so this case can't be closed from the dashboard. Sometimes a case's real finding is the gap in your observability.

07 · Case 4 · TCP

Refused and timed out, same box, same morning

target: qa-db.cliquidator.info → 192.168.20.191MySQL · Redis · RabbitMQ · NATS~33 services in qa2026-10-10
SequelizeConnectionRefusedError: connect ECONNREFUSED 192.168.20.191:3306

Ask the room
"Refused" errors ran from 05:00 to 08:13 UTC. "Timed out" errors ran from 05:00 all the way to noon. What was the box doing in each of those windows?
Refused means a packet reached a running host and its kernel answered with a RST: "I'm here, but nothing is listening on that port." The machine was up and the database, queue, and cache daemons were down. Timed out means nothing answered at all. The host was down, rebooting, or unreachable, so SYNs went into the void. Refused errors stopping at 08:13 while timeouts kept going suggests the host itself stopped answering after that point. Notice that DNS was fine the whole time: every line has the IP in it. The failure is a rung below that.

09 · Case 6 · TLS?

1.27 million TLS errors, and nothing is broken

kargo api · qa-greencliquidator nginx · aws-devrung 3 · handshake (supposedly)
# A: kargo, ~1.27M this week, almost exactly equal counts from each of 7 node IPs
http: TLS handshake error from 10.101.x.x:…: EOF
# B: nginx, ~200 over 48 minutes, one client
SSL_do_handshake() failed (SSL routines::no shared cipher) while SSL handshaking, client: 192.168.34.x, server: 0.0.0.0:443
peer closed connection in SSL handshake (104: Connection reset by peer)
Ask the room
These are the two biggest sources of "TLS errors" in our logs this week. Neither one is a cert problem. What are they?
Ask who the client is before you debug the server.
  • A: EOF means the client opened TCP and hung up before sending a ClientHello. Every node IP, at the same steady rate, is the signature of a TCP health check (a load balancer or kube-proxy probe) hitting an HTTPS port. The connection is the whole check. It's harmless, just noisy.
  • B: The access log shows that client's user agent: Tenable … Security. It's a vulnerability scanner deliberately offering weak ciphers to confirm the server refuses them. "No shared cipher" is the server passing the test.
🥚 Easter egg
One real TLS finding did turn up this week: Warning: Setting the NODE_TLS_REJECT_UNAUTHORIZED environment variable to '0' makes TLS connections and HTTPS requests insecure, from a staging service. That's the process-wide hammer from TLS in Depth's Node.js slide, live in our logs. The scoped fix is still NODE_EXTRA_CA_CERTS.

10 · Case 7 · TCP

Broken pipe on the first query after a quiet spell

service: authentication (Go)pods 10.102.x → DB in legacy VPC 10.0.x~2k pairs in production
[mysql] packets.go:155 write tcp 10.102.21.38:58948->10.0.5.86:3306: write: broken pipe
connection.go:801 closing bad idle connection: connection reset by peer
# Node's version of the same thing, seen in qa this week:
SequelizeDatabaseError: read ECONNRESET
Ask the room
DNS resolves, the port is open, and most queries work. The errors cluster on the first query after the pool has been idle a while. What's going on?
An idle-timeout mismatch. The pool keeps connections open longer than the database, or something in the cross-VPC path, is willing to. The far side quietly drops the idle connection. The client doesn't find out until its next write hits a dead socket: broken pipe, then reset. The Go driver retries on a fresh connection, so users mostly never notice, but the logs do. Fix it at the client by setting db.SetConnMaxIdleTime() and SetConnMaxLifetime() shorter than the server's wait_timeout and any LB or NAT idle timeout in the path.
A case from this same week: after a gateway migration, Tableau refreshes against a marketing DB failed with two look-alike errors that had two separate causes. MariaDB's wait_timeout was 300s, while Tableau reuses connections for 30–120 minutes. An ALB idle timeout of 60s was cutting off a 177-second refresh. The rule that fixed both: every hop's idle timeout has to outlast the hop in front of it. Backend keepalive should be longer than the LB idle timeout, and the LB idle timeout should be longer than the longest request.

11 · Case 8 · TCP vs. App

Two "upstream timed out" errors, two different rungs

apisix-internal · qawww / apisix-public · prod
# A: apisix-internal in qa, ~42 this week
upstream timed out (110: Connection timed out) while connecting to upstream, client: 10.101.22.x, request: "GET /purplewave-public/v1/excom/config", upstream: "https://10.0.0.88:443/v1/excom/config"
# B: www in prod, ~1.7k this week
upstream timed out (110: Connection timed out) while reading response header from upstream, server: www.purplewave.com
Ask the room
Same errno (110), same opening words. Which rung is each one on, and what's suspicious about the addresses in A?
The phrase after the comma tells you which rung. "While connecting": the SYN was never answered. That's rung 2, a security group, NACL, or route. "While reading response header": TCP and TLS both succeeded and the app was slow to answer. That's rung 4, so look at the app and its dependencies, not the network.

The addresses in A: the client is 10.101.x, the QA cluster, and the upstream is 10.0.0.88, a production EC2 range. The security group blocking that path is doing its job. The real bug is a QA route config pointing at a prod host. It looks like a network block, but it's a config bug.

🥚 Easter egg
nginx has two more upstream phrasings worth memorizing. upstream prematurely closed connection while reading upstream means the backend hung up mid-response, usually because it crashed or hit its own timeout. no live upstreams while connecting to upstream means nginx had already marked every backend as failed, so it didn't even try. That error is a downstream effect of something earlier, so look further back in the log.

12 · Case 9 · App behind a proxy

The 502 spike that was a deploy

prod EC2 · release automation2026-10-09 15:13–15:24 UTC502s: ~1k/day → ~61k that day
# socket-proxy access log: the symptom
"GET /v2/invoices/…" 502
# nginx error log, same minute: the cause
[crit] connect() to unix:/var/run/workflow-service/workflow-service.sock failed (2: No such file or directory) while connecting to upstream, server: dashboard.purplewave.com
Clue 1 · who said it
The 502 came from the proxy, and a 502 is the proxy reporting that the thing behind it failed. The access log only shows the symptom, so go to the proxy's error log for the same minute.
Clue 2 · the errno sequence
Over the 11 minutes, the same sockets (invoice, lead, contract, commission, apf, saved-search, note) cycle through three errnos. (2: No such file or directory): the socket file is gone because the process is stopped. (111: Connection refused): the file is back but nothing is accepting yet. (13: Permission denied): briefly recreated with the wrong owner (43 hits).
Clue 3 · when
The window lines up exactly with a release-automation run on those hosts.
Verdict
Services were restarted in place with no draining, so nginx kept sending traffic to sockets that didn't exist yet. It's the same refused-vs-missing logic as Case 4, on a Unix socket instead of a TCP port. The access log tells you that it broke. The error log tells you why.
Walking the ladder for this case · illustrative output
# on the EC2 host, mid-deploy
# rung 4 · app, through the proxy
$ curl -s -o /dev/null -w '%{http_code}\n' https://dashboard.purplewave.com/v2/invoices/health
502
# rung 2 · port: for a unix socket, nc -U replaces host:port
$ nc -zU /var/run/invoice-service/invoice-service.sock
nc: unix connect failed: No such file or directory
# ✗ errno 2: the socket file doesn't exist, because the service is stopped
# a few seconds later:
$ nc -zU /var/run/invoice-service/invoice-service.sock
nc: unix connect failed: Connection refused
# ✗ errno 111: the file is back, and nothing is accepting yet
$ sudo -u nginx nc -zU /var/run/invoice-service/invoice-service.sock
nc: unix connect failed: Permission denied
# ✗ errno 13: it works as root and fails as the nginx user, so the socket's owner is wrong
# after the deploy settles:
$ curl -s -o /dev/null -w '%{http_code}\n' https://dashboard.purplewave.com/v2/invoices/health
200

connect() to [2606:4700::6812:xxxx]:443 failed (101: Network unreachable) while connecting to upstream
upstream server temporarily disabled while connecting to upstream
dial tcp [2606:50c0:8000::154]:443: connect: network is unreachable # pkg-containers.githubusercontent.com
Clue 1 · exact words
Errno 101 isn't refused (111) and it isn't timed out (110). The packet never left the machine, because the local routing table has no route to that destination at all.
Clue 2 · look at the address
Those are IPv6 addresses (Cloudflare and GitHub). DNS returned an AAAA record alongside the A record, and the client tried IPv6 first. dig AAAA host and ip -6 route on the pod or node confirm it: there's an address, but no route to it.
Verdict
Nothing upstream is down. nginx marks the IPv6 peer as failed and falls back to IPv4, which works, so all you see is steady low-level noise. Fix it by resolving IPv4 only (nginx resolver … ipv6=off;), or by giving the network real IPv6. Either way, the error is a rung-1 answer meeting a rung-2 limitation.
Walking the ladder for this case · illustrative output
# from a kargo pod

$ dig +short AAAA pkg-containers.githubusercontent.com

# rung 2 · port, IPv6 vs. IPv4
$ nc -6 -zv pkg-containers.githubusercontent.com 443

$ nc -4 -zv pkg-containers.githubusercontent.com 443

# why v6 fails instantly:

::1 dev lo proto kernel metric 256 pref medium
# ✗ there's no IPv6 default route, only loopback. The v6 packets never leave the pod.

When Cloudflare can't get an answer from our origin, it says which rung failed in the status code itself. The counts are from this week, almost all in staging.

Ask the room
35,700 connect timeouts (522) to staging hostnames like dev-v2., dashboard., and www.cliquidator.info, each getting about 500 hits from about 350 user agents. Is staging on fire?
No. Those are abandoned DNS records for dev environments that no longer exist, and they're being hit by uptime bots and scanners (MonsidoUptime and friends), not people. The 530s on es-aws. and redis-aws. are the same story one rung up. The real fix is cleaning up DNS, and that's more than housekeeping. A dangling record that points at an address or service we no longer control is how subdomain takeovers happen.

Wrap-up

The field guide

Lessons that showed up more than once this week. None of them needed a new tool, only a careful read of the error.

The name in the error is the one the code used
Deleted databases, usernames passed to DNS, stale service URLs. Read the name before blaming the resolver.
The words after the comma give more detail
Refused vs. timed out vs. unreachable. "While connecting" vs. "while reading." ENOTFOUND vs. EAI_AGAIN.
Who said it, and who is the client?
Proxies report on what's behind them. Health checks and scanners make most of the TLS noise.
Time and blast radius
Many services failing together means a shared dependency. Find the first error in the window, not the loudest. Timeouts and retries have to nest.
