01 · Foundations

DNS is just a lookup table for the internet

Computers route by IP address. Humans remember names. DNS is the phone book that converts app.purplewave.com → 10.4.2.17 (or whatever it's hosting behind).

you type
app.purplewave.com
→
DNS resolution
→
an IP address
→
TCP connection
Nothing loads a webpage without this step happening first — even "the site is down" is often actually "DNS couldn't resolve."
Ask the room
Someone typo'd app.purplewave.con (not .com). Four different tools reported it four different ways — what do you think each one said, and are they actually describing the same underlying failure?
# Chrome
???
# dig
$ dig app.purplewave.con +short
???
# nslookup (Windows)
$ nslookup app.purplewave.con
???
# curl
$ curl https://app.purplewave.con
???
# Chrome
This site can't be reached app.purplewave.con's server DNS address could not be found. DNS_PROBE_FINISHED_NXDOMAIN
# dig
$ dig app.purplewave.con +short
;; ->>HEADER<<- ... status: NXDOMAIN
# nslookup (Windows)
$ nslookup app.purplewave.con
Server: 10.10.0.53 Address: 10.10.0.53#53 *** 10.10.0.53 can't find app.purplewave.con: Non-existent domain
# curl
$ curl https://app.purplewave.con
curl: (6) Could not resolve host: app.purplewave.con
All four are the same failure — the name simply doesn't exist (NXDOMAIN) — just reported in each tool's own words. Different from a SERVFAIL (the resolver itself errored) or a timeout (nobody answered at all).
02 · Primary DNS Server

Your laptop asks someone — who is that?

Every device has one or more configured DNS servers (see it in ipconfig /all or scutil --dns). That's your resolver — usually your router, VPN, or corporate DNS, which then asks the real internet on your behalf.

Your laptop
→
Configured resolver
e.g. 10.10.0.53
→
Root servers
→
.com TLD servers
→
purplewave.com
authoritative server
Beginner takeaway core
The resolver does the legwork so your laptop doesn't have to know the whole internet's structure.
Deeper detail
This chain is recursive resolution. Each server only knows "ask that other guy next" — nobody holds the whole map.
Ask the room
If two people on the same WiFi run nslookup www.purplewave.com, but one is on the VPN and one isn't — will they get the same answer?
Not necessarily. VPN traffic often points at an internal resolver that knows internal/private zones; off-VPN, that name may not resolve at all, or a public resolver might return something totally different (or NXDOMAIN). Same name, different resolver, different truth.

Zscaler is especially bad about this — we'll talk about it separately down the road.

03 · Behavior

Caching: everyone remembers, for a while

DNS answers get cached at every layer to avoid re-asking constantly: the browser, the OS resolver, the corporate/ISP resolver, and even intermediate servers. The TTL on the record tells each layer how long it's allowed to keep the answer.

browser cache
→
OS cache
→
resolver cache
→
authoritative server
(ground truth)
Only that last hop is authoritative. Everything before it is a guess based on "last time I checked, this was the answer." ipconfig /flushdns or sudo dscacheutil -flushcache clears your local layer only — not everyone else's.
Ask the room
A record's IP changes at 2am for a failover. Your laptop looked it up at 1:55am with a 3600s TTL. When do you see the new IP?
Not until your cached entry expires — up to ~55 minutes later (1 hour TTL minus the 5 minutes already elapsed), unless something flushes the cache sooner. This is exactly why low TTLs get set before planned cutovers.
04 · Record Types

The A record: name → IP, full stop

The most basic DNS record. It maps a hostname straight to an IPv4 address (AAAA does the same for IPv6).

NameTypeValueTTL
app.purplewave.comA203.0.113.42300
vpn.purplewave.comA198.51.100.73600
05 · Record Types

CNAME: name → another name

A CNAME doesn't point to an IP — it points to another hostname, which then gets resolved itself. Useful for pointing at things you don't control the IP of (a CDN, a load balancer, SaaS).

www.purplewave.com
CNAME →
d111abc.cloudfront.net
A →
actual IP
Route53 Alias AWS-specific
Not a real DNS record type — Route53's own trick to point a zone's apex (bare domain, no www) at an AWS resource like CloudFront or an ALB, because a real CNAME can't legally sit at the zone apex. Behaves like a CNAME but resolves server-side.
Cloudflare "proxied" (orange cloud) masking
When proxied, the A/CNAME Cloudflare publishes is a Cloudflare edge IP, not your origin's real IP. Your true server is hidden behind it — traffic, and attacks, hit Cloudflare first.
Ask the room
dig shop.example.com returns an IP owned by Cloudflare, not the company's known hosting provider. What's actually going on?
The record is almost certainly Cloudflare-proxied. The public DNS answer intentionally isn't the origin server — it's Cloudflare's edge, which terminates TLS, maybe caches content, and forwards to the real backend over a connection you can't see from outside.
06 · Tools

Verifying DNS truth without incomplete errors

Instead of trusting the browser, ask the resolver yourself. This is the single most useful skill for debugging "it works for me."

$ dig app.purplewave.com +short
203.0.113.42
# quick answer, no metadata
$ dig app.purplewave.com
;; ANSWER SECTION: app.purplewave.com. 300 IN A 203.0.113.42
# full answer: shows TTL (300s), record type, which server answered
$ nslookup app.purplewave.com
Server: 10.10.0.53 Address: 10.10.0.53#53 Non-authoritative answer: Name: app.purplewave.com Address: 203.0.113.42
dig is the operator's tool (Linux/Mac, more detail, scriptable). nslookup ships on Windows too and is fine for quick checks. dig +trace walks the whole root→TLD→authoritative chain live.
Ask the audience
What do you think this actually means?
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 12345 ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 0 ;; QUESTION SECTION: ;foo.example.com. IN A ;; ANSWER SECTION: foo.example.com. 300 IN CNAME ://target.com.
Two things are wrong at once, and both are real-world misconfigurations:

1) status: NXDOMAIN next to a non-empty ANSWER SECTION isn't a contradiction — the queried name (foo.example.com) does have a CNAME, but the name it points to doesn't exist. dig still shows you the CNAME hop it found before hitting the dead end.

2) The CNAME target itself, ://target.com., is not a valid hostname — someone pasted a URL fragment (missing the scheme, like https) into a field that's supposed to hold a bare domain name. CNAME values are names, never URLs.

07 · Behavior

Search path: how a bare hostname gets completed

Type jira instead of jira.purplewave.com and it still resolves? Your resolver's DNS search suffix list tries appending domains until one answers.

# resolv.conf / adapter DNS suffix
search purplewave.com corp.purplewave.com
$ ping jira → tries:
jira.purplewave.com ✗ maybe jira.corp.purplewave.com ✓ found it
Ask the room
A teammate on a different VPN profile types jira and gets "server not found," but it works for you. Same laptop model, same network. Why?
Different search domain configured for that VPN profile — the suffix list being appended doesn't include the domain where jira actually lives, so it never even tries the right full name.
🥚 Easter egg
On the same network, no VPN tricks involved, a phone and a computer can get different results for the same bare hostname — Android specifically ignores the DHCP-provided search suffix (never appends it), while iOS/macOS apply it inconsistently depending on how the network was joined. Same DHCP answer, different OS behavior.
08 · Naming

Reading a domain name, right to left

A hostname is a hierarchy. Each label is a step deeper, and each level can be delegated to a different owner or team.

app.internal.purplewave.com
↑ 3rd-level / subdomain — "app" bucket, owned by a team
↑ 2nd-level — "internal", could be its own delegated zone
↑ registered domain — purplewave.com, what you actually bought
↑ TLD — .com, sold by a registry
"Third-level domain" = the label just under your registered domain — e.g. internal in app.internal.purplewave.com. Companies often carve these off for a reason: internal. for private-only stuff, staging. for pre-prod, a region code, a team name.
Ask the room
What would be a good use-case for 3rd-level domains at Purplewave?
Consistent addresses throughout the product promotion path:
servicename.qa.purplewave.com servicename.staging.purplewave.com servicename.prod.purplewave.com
Same service name, same registered domain — only the environment label changes, so nobody has to guess the address moving between stages.
09 · Internal Zones

Private hosted zones: DNS that only exists inside your network

Route53 (and most DNS providers) let you create a zone that's only answerable from inside a VPC/VPN — the public internet gets NXDOMAIN, but internal clients get a real answer. Getting different answers for the same name depending on where the query comes from is generally called split-horizon DNS.

Public zone: cliquidator.info
NameTypeValue
wwwA203.0.113.42
Private zone: cliquidator.info VPC-only
NameTypeValue
wwwA10.4.1.9
gw-qaA10.4.2.5
Ask the room
Why would we want the answers to be different inside and outside the company?
A few overlapping reasons, all valid at once:
  • Performance — we don't want local traffic routing all the way out to a region like Virginia and back just to reach something sitting right next to it.
  • Security — we don't want purely internal traffic riding the public internet at all, even encrypted.
  • Security — we want the ability to inspect our internal traffic, which only works if that traffic actually flows through infrastructure we control.
🥚 Easter egg
Why different answers in different places inside AWS? A private hosted zone isn't one global answer — it's only associated with the specific VPCs you attach it to. You can have multiple PHZs for the same domain, each associated with a different set of VPCs, and each can hold different records. A resource in VPC A gets whatever's in the PHZ(s) associated with VPC A; a resource in VPC B — even in the same account, same region — gets whatever's associated with VPC B. If a name resolves in one environment's pod but not another's EC2 instance, check which VPC each one actually lives in and which PHZs are associated to it, not the record itself.
10 · Overrides

/etc/hosts: skip DNS entirely, locally

Before any DNS query is sent, your OS checks a local static file. An entry there wins — no network round trip, no cache, no TTL, just an instant match.

# macOS / Linux: /etc/hosts
127.0.0.1 localhost 10.4.2.5 jira.internal.purplewave.com 203.0.113.99 app.purplewave.com
# Windows: C:\Windows\System32\drivers\etc\hosts
10.4.2.5 jira.internal.purplewave.com
Classic uses: testing a site against a not-yet-live server, blocking a domain locally, or working around a broken/hijacked DNS answer by hardcoding the truth yourself.
Ask the room
A dev swears app.purplewave.com points to the new server. dig from the same laptop shows the old IP. Who's lying?
Neither, probably. dig talks straight to DNS and bypasses hosts entirely — so it can show a totally different answer than what the browser actually uses. Check /etc/hosts (or hosts file) first; a stale entry there explains the mismatch.
11 · Overrides

curl --resolve: a one-request override, no file editing

Same idea as /etc/hosts, but scoped to a single command — great for testing a server before its DNS is live, or bypassing a broken/hijacked resolver just to test.

$ curl --resolve app.purplewave.com:443:203.0.113.99 https://app.purplewave.com/health
# forces this one request to use .99, but the TLS cert still has to match app.purplewave.com
Beginner takeaway core
Lets you test "is the new server actually working" before flipping DNS — without touching any config files.
Deeper detail
Also the fastest way to prove "is this a DNS problem or an app problem" — if --resolve-ing straight to the known-good IP fixes it, DNS was the culprit.
Ask the room
Why might this not work when doing this from a developer's workstation at Purplewave, even though it does from the staging server, or from a Kubernetes pod?
Several things can quietly win over your --resolve flag or the request itself before it reaches the target:
  • /etc/hosts — a stale local entry can still redirect or short-circuit the connection
  • Zscaler — TLS inspection/proxying on the workstation intercepts the connection regardless of what IP curl was told to use
  • Route53 private hosted zone mapping — the workstation isn't on the VPC/VPN that would resolve to the internal target, so the TLS cert or routing context won't line up
  • Typos — the classic: wrong port, wrong scheme, or a hostname that doesn't match the cert
The staging server and the pod skip all of this because they sit inside the network path the request actually needs.
12 · The Twist

Zscaler and "DNS hijacking" — on purpose, by policy

Corporate security tools like Zscaler often act as a transparent DNS (and TLS) intermediary. Your device asks for a name; Zscaler answers with its own IP instead of the real one, then proxies the connection so it can inspect traffic.

you query
github.com
→
Zscaler resolver
(intercepts)
→
Zscaler proxy IP
not github's real IP
→
real github.com
(on your behalf)
This is why dig from a Zscaler-managed machine can lie to you. The answer is technically correct for that network's policy — it's just not the record the rest of the internet sees. It's the same mechanism a malicious hijack would use; the difference here is it's sanctioned, logged, and reversible by disconnecting/exempting Zscaler.
Ask the room
Everything about this app looks correct. I can get to it, internal DNS is set up — but I'm still getting NXDOMAIN on my workstation. What's going on?
Zscaler proxies the traffic on the back end — and if it can't reach the end resource itself, it won't resolve the DNS name at all. That surfaces as NXDOMAIN and looks exactly like a DNS problem, when the actual cause could be something else entirely: a security group, a routing table, a firewall rule. Don't stop at "DNS is broken" — check whether Zscaler itself can reach the target before chasing the DNS config.
🥚 Easter egg — pseudo-hijacking, closer to home: Kubernetes
Zscaler rewrites DNS on purpose from outside your app. Your own platform does something structurally similar, on purpose, from inside it: why does nats-auth-service work as a URL in a configMap? That's the Kubernetes cluster DNS resolver — same search-path idea from earlier, just scoped inside the cluster. The pod's resolv.conf appends namespace/cluster suffixes until something answers; what's actually being resolved is nats-auth-service.production.svc.cluster.local. Nothing hijacked it maliciously — the cluster's own DNS just completed the name the same way a corporate search suffix would.
🥚 Easter egg — pseudo-hijacking, closer to home: nginx
Same idea, one layer down: http://elasticsearch in an nginx config usually isn't DNS at all — it's an nginx upstream block, a label defined locally in nginx's own config and mapped to real backends before DNS ever gets a say. Grepping DNS records for it comes up empty; the redirect lives in the nginx config itself.
13 · Email & Trust

SPF, DKIM, DMARC: DNS proving "this email is legit"

These are just TXT records — but they're how the entire email industry decides whether to trust a message claiming to be from your domain.

RecordAnswersExample (TXT)
SPFwhich servers may send as this domain"v=spf1 include:_spf.google.com -all"
DKIMwas this message tampered in transit?selector._domainkey → "v=DKIM1; p=MIIBIjAN..."
DMARCwhat to do if SPF/DKIM fail"v=DMARC1; p=reject; rua=mailto:dmarc@purplewave.com"
These three together are why a spoofed "billing@purplewave.com" email gets rejected or quarantined at most vendors: it fails SPF/DKIM alignment, and a DMARC policy of p=reject tells receivers not to deliver it. This only works because the policy lives in DNS, publicly, for any mail server to check.
Wrap-up

The mental model to keep

Resolution
Every name walks resolver → root → TLD → authoritative, unless something short-circuits it (hosts file, --resolve, cache).
Records
A = IP. CNAME = another name. Alias/proxy = "the published answer isn't the real backend."
Trust
DNS isn't just addressing — SPF/DKIM/DMARC turn it into an identity and authorization system.
Interception
Zscaler-style hijacking is normal corporate DNS — same mechanism as an attack, opposite intent.
Next time something "isn't resolving right": dig it, check the hosts file, check the search suffix, then ask whether something in the middle (VPN, Zscaler, proxy) is answering instead of the real authority.
