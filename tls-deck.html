01 · Foundations (kept short)

The four ideas under all of TLS

A layman's pass — enough to follow the handshake and the debugging later, not a cryptography course.

Symmetric encryption
One key locks and unlocks. Fast. Problem: both sides need the same key — and getting it to the other side safely is the hard part.
Asymmetric encryption
Two keys: a public one anyone can use to lock, a private one only you hold to unlock. Solves the sharing problem. Slower — too slow for bulk data.
Hashing
A one-way fingerprint of data. Same input always gives the same hash; change one byte and the hash is completely different. Can't be reversed back to the original.
Digital signature
Hash the message, then encrypt that hash with your private key. Anyone with your public key can verify it — proving both who sent it and that it wasn't altered.
Ask the room
If asymmetric crypto is the "slow" one, why doesn't every HTTPS page feel slow?
Asymmetric crypto is only used briefly, during the handshake, to safely agree on a shared secret. Once that's done, both sides switch to fast symmetric encryption for the actual data. TLS uses the slow, safe method just long enough to bootstrap the fast one.
02 · Foundations (kept short)

The handshake: who says what, in what order

Skipping the math — this is about the message exchange. Simplified (TLS 1.2-style) for clarity.

Client:
ClientHello
→
Server:
ServerHello + certificate
→
Client validates
the cert chain
→
Key exchange
→
Finished
(both sides)
TLS 1.3 collapses several of these round trips, but the sequence of ideas is the same: say hello and list capabilities, present identity, verify identity, agree on a shared secret, confirm.
Ask the room
At what exact point does the client actually decide whether it trusts the server?
Right after it receives the certificate in ServerHello — before any key exchange finishes, before any application data flows. Chain validation happens at that point in the exchange, not at "the handshake completing." A trust failure here aborts the connection immediately; nothing encrypted with the session key is ever sent.
03 · PKI

Root, intermediate, leaf: why the chain exists

Your OS/browser ships with a small set of trusted root CAs. Roots almost never sign server certs directly — they sign intermediate CAs, which sign the actual leaf (server) certificate you get.

Root CA
in OS trust store
signs →
Intermediate CA
signs →
Leaf cert
(your server)
Keeping roots offline and rarely used limits the blast radius if a CA is compromised — only the intermediate needs to be revoked, not the root everyone trusts.
The order the server actually sends certs in
Order is absolutely critical: each certificate must sign the one before it, ending in a root that the client machine's own CA store has to already trust.
  1. Server (leaf) certificate
  2. Intermediate certificate(s)
  3. Root certificate
If the server forgets an intermediate, you get an untrusted/incomplete chain error even though the root is trusted — clients generally won't go fetch a missing intermediate on their own. Sending the full chain, every time, is the server's job.
04 · Certificates

x.509: the fields that actually matter

A certificate is mostly metadata plus a signature. These fields cause the vast majority of real-world problems.

FieldWhat it means
CNCommon Name — historically "the hostname"
SANSubject Alternative Name — the list of hostnames/IPs this cert is valid for
Not Before / Not Afterthe validity window — expiration lives here
Fingerprinta hash of the whole cert (usually SHA-256) — a unique thumbprint for pinning/verification
Issuerwho signed this cert — the first place to look when chasing an untrusted-authority error
Key Usage / EKU / Constraintswhat the cert is allowed to be used for (server auth, client auth, code signing...) and whether it's allowed to sign other certs at all (CA:TRUE/CA:FALSE) — a valid, trusted, correctly-named cert still fails without serverAuth, and a leaf cert flagged CA:TRUE breaks chain validation
Subject/Authority Key IDhashes of this cert's key and its issuer's key — how chain-building actually matches a cert to its issuer, especially during a CA key rotation
Public Key AlgorithmRSA vs. ECDSA, and key size — a factor in cipher/protocol negotiation, not just identity
Ask the room
Browsers stopped trusting the CN field for hostname matching years ago. What field actually decides whether a hostname matches now?
SAN — Chrome deprecated CN-based matching in 2017 (Chrome 58); modern clients only check the SAN list. A cert with a perfect-looking CN but no matching SAN entry will still fail hostname validation. If you're issuing or debugging certs, SAN is the field to check first — CN is legacy decoration at this point.
05 · Debugging

This is the real subject: five buckets of failure

Everything above was setup. In practice, almost every TLS error you'll ever see falls into one of five buckets — the rest of this session is each one, in detail, with the tools to tell them apart fast.

1. Untrusted authority
Client doesn't trust whoever signed this cert.
2. Cipher / protocol mismatch
Client and server can't agree on how to talk at all.
3. Hostname mismatch
The cert is valid and trusted — just not for this name.
4. Expired or revoked
The cert was fine once; it isn't anymore.
5. Networking issues
Nothing wrong with the cert at all — the handshake never got far enough to matter.
The error message rarely says which bucket you're in plainly — part of the skill is reading past the wording to the actual cause.
06 · Debugging

Bucket 1: untrusted authority

The client doesn't have (or doesn't trust) whoever signed this certificate — a missing intermediate, a private CA, or a self-signed cert nobody told the client about.

# curl
curl: (60) SSL certificate problem: unable to get local issuer certificate
# browser
NET::ERR_CERT_AUTHORITY_INVALID
Ask the room
curl says "unable to get local issuer certificate," but the same URL works fine in Chrome on the same machine. What's different?
They don't share a trust store. Chrome ships and manages its own root/intermediate store (and is often more current); curl on Linux typically reads a system CA bundle (/etc/ssl/certs/ca-certificates.crt or similar) that can be outdated, missing a newer intermediate, or simply not have a private/internal CA installed. Same cert, two different judges.
🥚 Easter egg — the -k flag
curl -k (--insecure) skips certificate verification entirely — handy for confirming "is this actually a trust problem" while debugging. Don't leave it in a script or a healthcheck: that's disabling TLS verification permanently, not diagnosing anything.
🥚 Easter egg — not every app looks in the same place
Different runtimes and apps often have their own idea of where the CA store lives (a language runtime's bundled store, an app-specific config, an environment variable override) — separate from the OS trust store entirely. If everything else about the setup looks right and it's still failing, don't assume it's reading the store you think it is — track down which CA bundle that specific process is actually using.
07 · Debugging

Bucket 2: cipher / protocol mismatch

The handshake fails before certificates are even the issue — client and server simply don't have any TLS version or cipher suite in common.

javax.net.ssl.SSLHandshakeException: Received fatal alert: handshake_failure
# or, from OpenSSL's side:
error:1417C0C7:SSL routines: tls_process_client_hello:no shared cipher
Ask the room
What do these two errors usually mean (hint: they're related)?
curl: (35) OpenSSL/3.0.13: error:0A00010B:SSL routines::wrong version number
HTTP/1.1 400 Bad Request
Look at what actually got requested:
$ curl https://purplewave.com:80
$ curl -I http://purplewave.com:443
See the problem? Each one is talking the wrong protocol to the wrong port — TLS aimed at the plaintext port, and plain HTTP aimed at the TLS port. "Wrong version number" is OpenSSL's way of saying "I tried to read a TLS handshake and got plaintext instead"; a plain 400 Bad Request from a TLS-only port is the mirror image — a webserver reading raw HTTP text where it expected a handshake. Neither is really a cipher/protocol negotiation failure — it's the wrong protocol on the wrong port, port and scheme swapped.
08 · Debugging

Bucket 3: hostname mismatch

The cert is perfectly valid and fully trusted — it's just not issued for the name you actually connected to.

NET::ERR_CERT_COMMON_NAME_INVALID
# cert SAN: app.purplewave.com # you connected to: 10.4.2.17 (bare IP)
Ask the room
Chain is trusted, dates are fine, everything checks out — but the browser still throws a hostname mismatch. Why?
Trust and identity are two separate checks. The name the client actually asked for — a bare IP, an internal load-balancer alias, a Host header override — isn't in the cert's SAN list. A cert being validly signed says nothing about which names it's valid for; that's a completely separate comparison against SAN.
🥚 Easter egg — wildcards and blast radius
A wildcard cert (*.purplewave.com) isn't cryptographically weaker than a cert issued for one exact hostname — same algorithms, same trust rules. The difference is blast radius: a wildcard's private key is shared across every host using it, so if that key gets loose, finding and replacing it everywhere it was deployed takes far longer than rotating a single exact-host cert. Convenient to issue, slower to clean up if things go wrong.
09 · Debugging

Bucket 4: expired or revoked

The cert was fine once. Now it either aged out (Not After passed) or the CA actively pulled trust before that date (revocation).

# expired
NET::ERR_CERT_DATE_INVALID Not After : Aug 12 2026 (past)
# revoked
NET::ERR_CERT_REVOKED
Ask the room
The cert's dates look completely fine — Not After is months away — but the browser says revoked. How is that even checked?
Revocation is a separate, active check from expiration — via OCSP (a live query to the CA: "is this serial number still good?") or a CRL (a downloadable list of revoked serials). A CA revokes early for reasons expiration doesn't cover: private key compromise, mis-issuance, the domain changing hands. Some clients soft-fail (ignore an unreachable OCSP responder); browsers increasingly hard-fail. Expiration is a calendar date; revocation is the CA saying "actually, no" mid-lifetime.
🥚 Easter egg — what about the computer's clock?
A system clock too far off can absolutely make a valid cert look expired or not-yet-valid — that's a real, mundane cause worth checking. But you likely can't fix it by just setting the clock wrong to "trick" a browser into accepting an actually-expired cert: modern browsers cross-check time against sources like Roughtime and the server's own Date response header, not just the local clock alone.
10 · Debugging

Bucket 5: networking issues

The cert is fine. TLS itself is fine. The handshake never got far enough for either to matter — something below TLS killed the connection first.

# curl
curl: (35) OpenSSL SSL_connect: Connection reset by peer in connection to app.purplewave.com:443
# or, further along:
curl: (28) SSL connection timeout
Nothing about the certificate yet — a reset or timeout during the handshake usually means the connection never reached the TLS layer cleanly at all. Check basic reachability first: a security group or firewall rule blocking the port, a load balancer health-check or idle-timeout killing the connection mid-handshake, MTU/packet fragmentation, or a middlebox (proxy, another Zscaler-style inspector) actively terminating it. If the client never even got a ServerHello, the problem is below TLS — don't start debugging certs until you've confirmed the connection itself is stable.

11 · Tools

OpenSSL: talking to the server directly

openssl s_client performs the handshake by hand, so you see exactly what the server presents — no browser, no app-level retry logic hiding the real error.

$ openssl s_client -connect app.purplewave.com:443 -servername app.purplewave.com
CONNECTED(00000003) depth=2 C = US, O = Example CA, CN = Example Root CA verify return:1 --- Certificate chain 0 s:CN = app.purplewave.com i:CN = Example Intermediate CA 1 s:CN = Example Intermediate CA i:CN = Example Root CA ---
Ask the room
Why do I need -servername in addition to -connect host:port?
That's SNI (Server Name Indication). A single IP:port can host many TLS certificates for different domains (virtual hosting, shared load balancers, CDNs). Without -servername, the server doesn't know which cert to hand back — it may return a default/fallback cert, which then looks exactly like a hostname-mismatch bug when the real issue was a missing flag on your test command, not a server misconfiguration.
🥚 Easter egg — Zscaler strikes again
On a Zscaler-managed machine, s_client will happily show you a cert — just not the real one. Zscaler intercepts the TLS connection and re-signs it with its own certificate so it can inspect traffic. You can't get a trustworthy read on the actual server's cert chain from a Zscaler-intercepted connection; run it from somewhere off that path (a different network, a jump box, a container outside the proxy) to see what's really there.
12 · Tools

OpenSSL: reading and verifying what you got

Once you have the cert, these are the commands that answer "what does it actually say" and "does it actually chain to something I trust."

# dump human-readable fields (CN, SAN, dates, issuer)
$ openssl x509 -in cert.pem -noout -text
# just the validity window
$ openssl x509 -in cert.pem -noout -dates
# the SHA-256 fingerprint
$ openssl x509 -in cert.pem -noout -fingerprint -sha256
# does this chain actually verify against a CA bundle?
$ openssl verify -CAfile ca-bundle.pem cert.pem
# force a specific protocol version to isolate a cipher/protocol mismatch
$ openssl s_client -connect host:443 -tls1_2
Pull straight from the live server instead of a file with openssl s_client ... | openssl x509 -noout -text — useful when you don't have the cert on disk, just a hostname that's misbehaving.
🥚 Easter egg — stop asking for the cert
You shouldn't ever need to ask someone to send you a certificate off a running server. If it's live and reachable, openssl s_client fetches exactly what it's presenting, straight from the source — no waiting on a ticket, no risk of getting a stale copy someone had lying around.

The private key is a different story — that, you can't just fetch from a live connection. If it was regenerated fresh rather than renewed against the existing key, every place that needs it has to actually receive the new one; there's no shortcut around shipping it around securely.

13 · Tools

Verifying the entire chain

One cert at a time only tells you so much. This shows every certificate the server actually sent, in the order it sent them.

$ openssl s_client -showcerts -connect host:443 -servername app.purplewave.com
Same order as before — leaf → intermediate(s) → root — this just lets you see it directly from the server instead of taking it on faith.
🥚 Easter egg — yes, it's noisy
-showcerts dumps every cert in full — expect a wall of base64. You can narrow it down with the flags from the previous slide depending on what you're actually chasing (just the subject/issuer lines, just dates, just the chain depth) instead of reading the whole thing by eye every time.
14 · Language-Specific

Debugging TLS in Node.js

Node's TLS errors are usually verbose enough to name the bucket directly — the trap is the "fix" that's actually a much bigger hammer than intended.

ErrorBucket
UNABLE_TO_VERIFY_LEAF_SIGNATUREuntrusted authority — usually a missing intermediate
DEPTH_ZERO_SELF_SIGNED_CERTuntrusted authority — no CA at all, self-signed
ERR_TLS_CERT_ALTNAME_INVALIDhostname mismatch — check SAN
CERT_HAS_EXPIREDexpired
Ask the room
Someone "fixes" a Node cert error by setting NODE_TLS_REJECT_UNAUTHORIZED=0. What did they actually just break?
Every outbound TLS connection in that entire process, for the life of the process — not just the one request that had the problem. It disables certificate validation globally, so MITM protection is gone for every HTTPS call the app makes. The scoped fix is NODE_EXTRA_CA_CERTS pointing at the missing/private CA bundle, or passing a specific ca option to the one client that needs it.
15 · Language-Specific

Debugging TLS in Go

Go's crypto/x509 errors are usually precise about which bucket you're in — the classic trap here is environmental, not code.

x509: certificate signed by unknown authority
x509: certificate is valid for app.internal, not app.purplewave.com
Ask the room
A Go binary throws x509: certificate signed by unknown authority only when run inside a Docker container — never on the host it was built on. Why?
Minimal base images (scratch, a bare alpine without the ca-certificates package) don't ship an OS trust store. Go's x509.SystemCertPool() reads that OS store — on the build host it's populated; inside the stripped-down container it's empty or missing entries. Fix: install ca-certificates in the image, or bake a specific root pool into the binary via InsecureSkipVerify's much safer cousin, a custom RootCAs pool — never reach for InsecureSkipVerify: true as the fix.
Wrap-up

The mental model to keep

Crypto
Asymmetric bootstraps trust briefly; symmetric does the actual work — fast, once agreed on.
Chain
Trust flows root → intermediate → leaf. A missing intermediate breaks a client that trusts the root fine.
Identity ≠ trust
A validly signed, unexpired cert can still be for the wrong name. SAN decides identity; the chain decides trust.
Five buckets
Untrusted authority, cipher/protocol mismatch, hostname mismatch, expired/revoked, networking — nearly every real error is one of these.
Next time a TLS error shows up: openssl s_client -servername straight at it before touching any app code. It tells you the chain, the dates, and the negotiated protocol/cipher — usually enough to name the bucket in under a minute.
